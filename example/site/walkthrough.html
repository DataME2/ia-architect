Watch a change climb the ladder

Your first change, start to finish

One requirement, from "I want this" to a merged, deployed, documented change — showing exactly what you (Requester and Reviewer) do and what your AI Agent produces at each step. Same steps whether the Agent is an AI or a person.

The example we'll follow

Say you want to add a short, plain-language FAQ to this guidance site. Small, realistic, and it touches just enough layers to see the shape. Watch where you barely do anything and where your review is the thing that matters.

Requirement

You say what you want

Requester"People keep asking the same handful of questions — let's add a short FAQ to the site." A need, not a diff.
AgentRecognizes this as a change in requirements, so it does not jump to code. It opens the ea-first-change process.

ea-first-change · check the open-questions log first (this project keeps none, so there's nothing to reconcile)

Layer 1 · Strategy & Motivation

Why does this exist? Does it hold up?

AgentChecks the requirement against the goals and Principles. An FAQ serves Goal G1 — legible guidance, and violates no Principle (it links to sources, it won't publish unreviewed).
RequesterConfirm the "why." If the agent had found a Principle conflict, it would stop here and surface it to you instead of proceeding.

AgentNo change — same GitHub Pages hosting, same Actions deploy. A layer with nothing to change still gets an explicit "no change"; silence isn't a decision.

Record · before any code

Write the scope document

AgentWrites the next-numbered docs/scope/ doc: the five-layer verdict table above, plateaus, work packages, and — just as important — what's out of scope. This happens before implementation.

scope-doc

Implement & verify

Only now, write the code

AgentBuilds faq.html, keeping the EA and scope docs true to what's actually shipped. Then verifies: every element is named by a doc, every link resolves, the page renders.

Grounding rule: every code artifact is named by a doc, every doc element names its code — see ea-doc-style

Hand off

Open a pull request

AgentOpens a PR whose description covers the whole branch and mirrors the scope doc's layer table — so the review is a quick yes/no, not archaeology.

pr-description

Reviewer

You review and merge

ReviewerRead the PR, request changes or approve, and merge. This is the only step that ships anything — the agent has no merge rights. Speed with a seatbelt.

Principle P2 — no unreviewed content reaches the public site (why the agent stops at co-pilot)

Ship

It deploys itself

CI/CDMerging to main triggers the Pages workflow; the FAQ is live minutes later. Your total hands-on: describe it, review it, merge it.

Two skills for when it gets bigger

The happy path isn't the only path

Most changes look like the walkthrough above. Two situations bend it — and each has a skill your agent reaches for automatically.

stack-selection — you're at layer 5 with no stack chosen yet

When it triggers: bootstrapping a brand-new project, or reaching the Technology layer of a small app and finding no runtime, hosting, or CI decision on record.

What it does: instead of re-deriving a stack from scratch every time, it gives a decision framework with concrete defaults — static-only (GitHub / Cloudflare Pages, no backend) versus needs data or auth (managed Postgres + Auth like Supabase, hosted on Vercel) — and the reasoning for picking one.

What it produces: a recorded choice in docs/ea/5_technology/, so the next change inherits it instead of re-litigating it. This very site took the static-only branch — see its Technology layer.

stack-selection skill

story-sharding — a work package too big for one sitting

When it triggers: the scope document is written, but one of its work packages is too large or long-running to finish in a single session — the kind of thing where an agent (or a person) resuming later would have to re-derive the whole plan from the EA tree.

What it does: shards that work package into small, self-contained story files, each carrying enough context to be picked up cold — adapted from BMAD-METHOD's context-engineered development.

What it produces: a set of story files an agent or teammate can execute one at a time without losing the thread — so a big initiative survives being paused, handed off, or spread across many short sessions.

story-sharding skill
