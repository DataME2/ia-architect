# Decisions

_[← Repository README](../../README.md) · [Enterprise architecture](../ea/README.md)_

One file per decision, numbered chronologically, each explaining a single
call that's smaller than an initiative (see [docs/scope/](../scope/README.md))
but consequential enough that a future reader will ask "why this and not
the alternative?" — most often an AI actor's autonomy level or decision
rights (see `ea-doc-style`'s actor notation in
[docs/ea/2_business/](../ea/2_business/README.md)).

| 7   | [A tenant is created by an owner-issued invitation, not by signing up](./7_tenant-provisioning-by-owner-issued-invitation.md) | Accepted (August 2026) | Who may turn a club into a tenant, and how. Generalises [decision 6](./6_public-registration-through-a-scoped-function.md) one level up — an owner-issued single-use link separates *authorisation* (stays with the owner) from *typing* (moves to the club), and solves the bootstrap paradox inside the security model rather than by stepping around it with elevated SQL. **Not built** |
| 8   | [Demonstration access by anonymous session and a read-only role](./8_demo_access_by_anonymous_session_and_a_read_only_role.md) | Accepted (August 2026) | How a stranger sees the product without an account. An **anonymous Supabase session** makes `auth.uid()` real, so every existing policy applies unchanged and **no P5 exception is bought** — unlike letting `anon` read one club, which would put an `or` clause on 24 select policies forever. A **`viewer` membership** makes the visit read-only *by naming a role no write policy names*, so it needs no policy of its own and stays true for tables added later. The door is decision 6's shape again: one scoped write, club looked up rather than supplied. **Built**, proved by `supabase/tests/20_demo_front_door.sql` |
| 9   | [Platform administration provisions tenants and never reads inside one](./9_platform_administration_provisions_but_never_reads.md) | Accepted (September 2026) | The super-administration question [scope 28](../scope/28_onboarding-a-club-and-its-history.md) deferred. Settled by a distinction decision 7 noted in passing: **creating a tenant requires no ability to read inside one**, so the exception is drawn at *metadata* — club names and whether a club is finished — and never at tenant contents. A `platform_admin` allowlist the API cannot read or write in either direction, `security definer` functions that check it, and a separate identity **holding no `club_membership`**, which is what keeps the ordinary policies denying it. The console is a route in the same app, gated by authorisation rather than by an unpublished URL. **Built**, proved by `supabase/tests/23_platform_administration.sql` |
| 10  | [An account's identity is asserted, never inferred](./10_identity_is_asserted_never_inferred.md) | Accepted (September 2026) | How the platform learns that an account **is** a given Person — the gap that leaves [P1](../ea/1_strategy/1_motivation.md) unhonoured for the sign-in identity. Matching `person.email` to `auth.users.email` would close it in one statement and is refused: families share an inbox, `secretary@club.org.au` has had three holders, and `person.email` is typed by a registrar from a form — so a match would make anybody registering with the secretary's address *be* the secretary. An administrator asserts the link (BR107); it lives in its own table because `club_membership` is one row per role, and is unique in **both** directions (BR106); unlinked is shown as unlinked (BR108). **Built**, proved by `supabase/tests/25_account_person.sql` — [scope 29 WP1](../scope/29_actors-access-and-permissions.md) |
